# E2E-тесты проекта

В проекте используются E2E-тесты на Playwright.

E2E означает `end-to-end`, то есть проверку пользовательского сценария “от начала до конца” в настоящем браузере.

В отличие от unit-тестов, которые проверяют отдельные функции или куски бизнес-логики, E2E-тесты имитируют действия пользователя: открыть страницу, нажать кнопку, выбрать услугу, заполнить форму, отправить данные и увидеть ожидаемый результат.

## Зачем нужны E2E-тесты

E2E-тесты помогают проверить, что основные пользовательские сценарии работают целиком:

- страница открывается;
- приложение не падает;
- React ErrorBoundary не показывается;
- нужные кнопки и формы доступны;
- пользователь может пройти важный путь до конца;
- валидация формы срабатывает;
- переходы между страницами работают;
- адаптивная верстка не ломается на важных viewport-размерах.

В этом проекте E2E-тесты особенно важны для `/book`, потому что онлайн-запись состоит из нескольких связанных шагов: выбор услуги, даты, слота, формы, пакета и оплаты.

## Чем E2E отличается от Vitest

В проекте есть два уровня автотестов.

### Vitest

Vitest проверяет бизнес-логику, API-сценарии, backend-валидацию, платежную финализацию, webhook security, reminders, уведомления и вспомогательные функции.

Это быстрые тесты, которые хорошо подходят для проверки логики без запуска браузера.

### Playwright E2E

Playwright проверяет сценарии в браузере.

Он открывает страницы так, как это делает пользователь, нажимает кнопки, заполняет поля и проверяет результат на экране.

## Что покрыто E2E-тестами

### Публичные страницы

Проверяется, что основные публичные страницы открываются без падения приложения:

- главная страница;
- страница онлайн-записи `/book`;
- страница отзывов `/reviews`;
- страница успешной оплаты `/payment-success`;
- страница входа в админку `/admin/login`.

Также проверяется, что на страницах нет ErrorBoundary и они содержат ожидаемый контент.

### Защищенные admin routes

Проверяется, что неавторизованный пользователь не может попасть в закрытые разделы админки.

Проверяются маршруты:

- `/admin`;
- `/admin/requests`;
- `/admin/clients`;
- `/admin/services`;
- `/admin/sessions`;
- `/admin/notes`;
- `/admin/schedule`;
- `/admin/scheduler`;
- `/admin/reviews`;
- `/admin/help`.

Ожидаемое поведение: пользователь без admin session должен быть перенаправлен на login.

### Режимы `/book`

Проверяется, что страница `/book` открывается и основные режимы записи доступны:

- обычная запись;
- запись по пакету;
- покупка пакета.

Это защищает от ситуации, когда после изменений в данных, API или UI один из режимов перестает отображаться или ломает страницу.

### Валидация обычной записи

Проверяется сценарий обычной записи:

1. пользователь выбирает услугу;
2. выбирает доступную дату;
3. выбирает свободный слот;
4. открывается форма записи;
5. пустые обязательные поля подсвечиваются ошибками;
6. некорректный телефон не проходит валидацию;
7. некорректный email не отправляется браузером;
8. слишком длинное сообщение блокируется.

Этот тест защищает форму от регрессий в обязательных полях и клиентской валидации.

### Обычная запись с оплатой

Проверяется успешный сценарий обычной записи с переходом к оплате:

1. пользователь выбирает услугу;
2. выбирает дату;
3. выбирает слот;
4. заполняет имя, фамилию, телефон, email и сообщение;
5. выбирает предпочтительный способ связи;
6. принимает согласие на обработку персональных данных;
7. нажимает “Перейти к оплате”;
8. фронт отправляет `POST /api/payment?action=create`;
9. payload содержит данные выбранной услуги, слота и клиента;
10. пользователь попадает на `/payment-success`.

Этот тест не подключается к реальной ЮKassa. API оплаты мокается, чтобы проверить именно frontend-flow и корректность payload.

### Запись по коду пакета

Проверяется сценарий, когда клиент уже имеет выданный пакет:

1. пользователь выбирает режим “По пакету”;
2. вводит код пакета и контакт;
3. система находит пакет;
4. отображается информация о пакете;
5. показывается услуга, длительность и оставшееся количество сессий;
6. пользователь выбирает дату и слот;
7. форма открывается с предзаполненными данными клиента;
8. запись создается без перехода к оплате;
9. остаток сессий в пакете обновляется.

Этот тест защищает сценарий использования уже купленного пакета.

### Покупка пакета

Проверяется сценарий покупки нового пакета:

1. пользователь выбирает режим “Купить пакет”;
2. выбирает пакетный план;
3. заполняет форму;
4. выбирает предпочтительный способ связи;
5. принимает согласие;
6. нажимает “Перейти к оплате”;
7. фронт отправляет `POST /api/payment?action=create`;
8. payload содержит `paymentKind: "service_package"`;
9. payload содержит `packagePlanId`;
10. пользователь попадает на `/payment-success`.

Этот тест защищает отдельный payment-flow покупки пакета.

### Payment success page

Проверяется, что страница успешной оплаты открывается и отображает данные после оплаты.

В E2E для оплаты используется мок статуса платежа, чтобы не зависеть от реального платежного провайдера.

### Responsive smoke-проверки

Проверяется, что важные публичные страницы остаются usable на mobile и tablet viewport:

- нет горизонтального overflow;
- body виден;
- ErrorBoundary не появляется;
- основной ожидаемый контент отображается.

Это не заменяет ручную визуальную проверку, но помогает быстро ловить грубые responsive-регрессии.

### WebKit / Safari-like проверки

Отдельно добавлен WebKit-набор для Safari-like проверки публичных страниц, `/book` и ключевых mobile-взаимодействий.

WebKit используется как ближайшая автоматизированная проверка к Safari / iOS-поведению. Это не настоящий iPhone Safari на устройстве, но полезный слой автопроверок для тех мест, которые часто ломаются на iOS: mobile-меню, sticky/fixed элементы, viewport, touch-взаимодействия, custom select, checkbox и отсутствие горизонтального overflow.

Проверяются основные маршруты на viewport-размерах:

- iPhone 13 Pro Max: `428 × 781`;
- iPad 9: `810 × 948`.

WebKit-проверки не дублируют весь тяжелый Chromium payment-набор, чтобы не перегружать локальную разработку. Вместо этого они закрывают самые важные Safari-like риски.

Сейчас WebKit покрывает:

- открытие основных публичных страниц;
- отсутствие ErrorBoundary;
- отсутствие горизонтального overflow;
- отображение ожидаемого контента;
- mobile burger menu;
- переходы по пунктам mobile-меню;
- переход на `/book` через CTA внутри burger-menu;
- переход на `/book` через floating CTA;
- переключение языка RU / EN;
- переключение светлой и темной темы;
- открытие `/book` на iPhone и iPad viewport;
- обычную запись на консультацию без финальной отправки оплаты;
- выбор услуги;
- выбор доступной даты;
- выбор свободного слота;
- открытие формы обычной записи;
- заполнение полей формы обычной записи;
- переключение режимов `/book`;
- выбор пакетного плана;
- открытие формы покупки пакета;
- заполнение полей формы покупки пакета;
- работу custom select для предпочтительного способа связи;
- checkbox согласия.

Это не заменяет ручную проверку на реальном iPhone / iPad, но помогает быстрее ловить Safari-like регрессии в верстке и базовых взаимодействиях.

## Почему часть API мокается

Некоторые E2E-тесты используют mock API.

Это сделано осознанно, потому что цель этих тестов — проверить frontend-сценарий в браузере, а не заново тестировать backend, базу данных или платежного провайдера.

Например, для `/book` мокается:

- список услуг;
- доступность даты и слота;
- проверка пакета;
- создание записи;
- создание платежа;
- статус платежа.

Backend-логика отдельно покрыта Vitest-тестами.

Такой подход делает E2E:

- быстрее;
- стабильнее;
- легче для локального запуска;
- менее зависимыми от базы данных и внешних сервисов.

## Что E2E-тесты не проверяют

E2E-тесты в текущем виде не являются полной заменой ручному QA.

Они не проверяют:

- реальную оплату в ЮKassa;
- реальную доставку email через Resend;
- реальную доставку Telegram-уведомлений;
- полный admin CRM happy-path с созданием сущностей в базе;
- полный premium scheduler CRUD-flow;
- все возможные Safari / iPhone edge cases на реальном устройстве.

Эти зоны либо покрываются Vitest/backend-тестами, либо остаются для ручной проверки и будущего расширения E2E.

## Как запустить E2E-тесты

Запустить весь E2E-набор:

```bash
npm run test:e2e
```

Запустить весь E2E-набор в более легком локальном режиме:

```bash
npm run test:e2e -- --workers=1 --reporter=list
```

Запустить весь WebKit-набор:

```bash
npm run test:e2e -- tests/e2e/webkit --project=webkit-responsive --workers=1 --reporter=list
```

Запустить только WebKit responsive smoke:

```bash
npm run test:e2e -- tests/e2e/webkit/webkitResponsive.spec.ts --project=webkit-responsive --workers=1 --reporter=list
```

Запустить только WebKit-проверку обычной записи на `/book`:

```bash
npm run test:e2e -- tests/e2e/webkit/webkitBookingRegularFlow.spec.ts --project=webkit-responsive --workers=1 --reporter=list
```

## Рекомендуемая проверка перед важным коммитом

```bash
npm run test:e2e -- --workers=1 --reporter=list
npm run test
npm run build
```

## Как читать результат

Если тесты зеленые, значит основные пользовательские сценарии прошли.

Если тест упал, нужно смотреть:

- название упавшего теста;
- шаг, на котором он упал;
- текст ошибки;
- screenshot в `test-results`;
- `error-context.md` в `test-results`.

Папка `test-results` создается Playwright после падений и не должна коммититься.

Её можно удалить командой:

```powershell
Remove-Item -Recurse -Force test-results, playwright-report, blob-report -ErrorAction SilentlyContinue
```

## Текущая стратегия

Текущая стратегия тестирования:

- Vitest закрывает бизнес-логику, API и backend-сценарии;
- Chromium Playwright закрывает основные пользовательские E2E-сценарии;
- WebKit Playwright закрывает Safari-like responsive и interaction-проверки для публичных страниц, `/book`, mobile navigation, темы и языка;
- ручная проверка остается для визуальной полировки, сложных admin-flow и premium scheduler.

Такой баланс дает хорошее покрытие без чрезмерного утяжеления проекта и локальной разработки.
